3 Instrumentación con OpenTelemetry SDK

Se implementó un enfoque híbrido combinando auto-instrumentación para captura de infraestructura sin modificar el código de negocio, y custom spans para trazar la lógica de negocio crítica con atributos semánticos enriquecidos.

3.1 Auto-Instrumentación

4 OTel Collector: Configuración y Despliegue

El OTel Collector actúa como agente central de telemetría, recibiendo datos de ambos servicios vía OTLP gRPC y enrutando cada señal al backend correspondiente.

4.1 Pipeline de Configuración (GKE)

receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }

processors:
  memory_limiter:
    check_interval: 1s
    limit_mib: 512
    spike_limit_mib: 128
  resource:
    attributes:
      - { key: cloud.provider, value: "gcp", action: upsert }
      - { key: deployment.environment, value: "production", action: upsert }
  batch:
    timeout: 10s
    send_batch_size: 2048

exporters:
  otlp/jaeger:
    endpoint: jaeger-collector.observability.svc.cluster.local:4317
    tls: { insecure: true }
  prometheus:
    endpoint: "0.0.0.0:8889"
    resource_to_telemetry_conversion: { enabled: true }
  googlecloud:
    project: ${GCP_PROJECT_ID}

service:
  pipelines:
    traces:   { receivers: [otlp], processors: [memory_limiter, resource, batch], exporters: [otlp/jaeger] }
    metrics:  { receivers: [otlp], processors: [memory_limiter, resource, batch], exporters: [prometheus, googlecloud] }
    logs:     { receivers: [otlp], processors: [memory_limiter, resource, batch], exporters: [googlecloud] }
Despliegue: El Collector se despliega en el namespace observability del clúster GKE mediante el Helm chart versionado en helm/otel-stack/. La configuración completa está en otel-collector/config-gcp.yaml, versionada en el repositorio.

5 Correlación Cross-Signal

El trace_id generado por OTel SDK actúa como pivot universal que conecta los tres pilares de observabilidad para un mismo request HTTP:

1. Métrica → Alerta 2. Traza Distribuida 3. Log Estructurado
Grafana detecta latencia p95 > umbral en panel SLI-3. Se identifica el intervalo de tiempo afectado. En Jaeger UI se busca por trace_id. Se obtiene el span en cascada: service-a → service-b → PostgreSQL. En GCP Cloud Logging se filtra por jsonPayload.trace_id. Se obtiene el log exacto con el error y stacktrace.

5.1 Flujo de Diagnóstico Verificado

  1. Grafana detecta latencia elevada en el panel SLI-3: Latencia p50/p95/p99
  2. Se copia el trace_id del log estructurado en GCP Cloud Logging (campo jsonPayload.trace_id)
  3. Se pega en Jaeger UI → se obtiene la traza completa con todos los spans y su jerarquía
  4. Se identifica el span lento (fetch_item_from_db en service-b) con su db.statement exact
  5. Se correlaciona con la métrica db_client_operation_duration en Prometheus para confirmar el patrón

8 Decisiones de Diseño

DecisiónAlternativasJustificación
OTel SDK Python Datadog Agent, Dynatrace Vendor-neutral; permite custom spans sin acoplamiento a un proveedor específico
GKE (GCP) Cloud Run, Compute Engine Kubernetes nativo facilita Helm charts, namespaces de observabilidad y service discovery interno
Jaeger Zipkin, Tempo, Cloud Trace Compatibilidad OTLP nativa, UI rica para análisis de spans, completamente open-source
Prometheus + Grafana Cloud Monitoring, Datadog Estándar de facto en ecosistema Kubernetes; dashboards como código (JSON versionado en repo)
GCP Cloud Logging Loki, Elasticsearch Integración nativa sin infraestructura adicional; búsqueda directa por trace_id
W3C TraceContext B3 (Zipkin), Jaeger format Estándar IETF; adoptado por todos los instrumentadores OTel garantizando interoperabilidad

9 Conclusiones

  1. Independencia de Proveedor (No Vendor Lock-In): OpenTelemetry desacopla completamente el código de la aplicación de los backends de observabilidad. La misma instrumentación funciona con Jaeger, Tempo, Zipkin o cualquier backend compatible con OTLP, sin cambiar una sola línea de código de negocio.
  2. Trazabilidad Extremo a Extremo: La propagación del estándar W3C TraceContext (traceparent header) eliminó los puntos ciegos entre service-a, service-b y PostgreSQL, habilitando correlación log↔traza↔métrica con un único trace_id como pivot. Esto reduce el MTTR (tiempo medio de resolución) de incidentes de horas a segundos.
  3. Costo Marginal Justificado: El benchmark confirmó un overhead de ~33% en latencia y ~20% en throughput bajo 50 VUs concurrentes. Sin embargo, todos los SLOs críticos se mantienen cumplidos. Este costo operativo es completamente justificable frente al valor de detectar, localizar y resolver incidentes con observabilidad unificada en tiempo real.
  4. IaC Reproducible: Toda la infraestructura (GKE, Cloud SQL, Artifact Registry) está definida en Terraform versionado. Los servicios se despliegan mediante Helm charts parametrizados, permitiendo reproducir el entorno completo de forma determinista con terraform apply + helm upgrade --install.
